# Adding a Feature

The recipe for a new feature with its own table and endpoints, layer by layer and in an order where each file
compiles against the one before. [Architecture](architecture.md) explains why the layers look like this; this
page is the how.

Some features are not a stored resource. Read the matching pattern in [Architecture](architecture.md#design-patterns)
first when you need:

- a pluggable calculation: Strategy, see `service/mortgage/strategy/`;
- behaviour per demand type: `service/workflow/product/DemandTypeRegistry`;
- a new notification channel: Observer, see `service/notification/channel/`;
- an outside system or library: a port interface in `service/`, its adapter in `infrastructure/`;
- a new variant of a sealed type: see `DemandDetail`.

## Worked example: Activity Sector

Every step below is shown against the real `activity-sector` feature (`POST /api/v1/activity-sectors`,
`GET /api/v1/activity-sectors`), the smallest complete feature in the codebase at 14 Java files (about
390 lines) plus 8 i18n files. Use it as a template. Copy its files, rename things, adjust the fields, and you're
most of the way there.

## The order to build in (bottom-up: persistence → domain → API)

Building bottom-up just means every layer you write already has the thing below it to compile
against: no forward references, no guessing at a type that doesn't exist yet.

### 1. Liquibase changeset: the table

Start in `src/main/resources/db/changelog/db.changelog-master.yaml`. It holds `001-baseline` (the
whole schema and reference data) and `002-seed-dev-users` (local demo accounts, `dev` context only).
Append a new changeset at the end, id = next free number (`003-…` for the first one), and always write
a `rollback:`. Never edit a changeset that has already run on a shared environment (dev, uat, prod):
add a new one. Locally it doesn't matter: the `dev` profile drops and rebuilds the database on every
start. If the SQL differs between H2 (unit tests) and PostgreSQL, put a `dbms: h2` / `dbms: postgresql`
attribute on each `sql` block, as the baseline does. Public API ids are always
`UUID` (the `public_id` column, generated in code, see step 3). Never the `BIGINT id`. More on that
convention below.

```yaml
- changeSet:
    id: "003-create-my-feature"
    author: bladi
    changes:
      - sql:
          sql: |
            CREATE TABLE IF NOT EXISTS activity_sector (
              id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
              name       VARCHAR(100) NOT NULL,
              created_at TIMESTAMP NOT NULL,
              public_id  UUID NOT NULL,
              CONSTRAINT uq_activity_sector_public_id UNIQUE (public_id)
            );
            CREATE UNIQUE INDEX IF NOT EXISTS idx_activity_sector_name ON activity_sector (name);
    rollback:
      - sql:
          sql: |
            DROP INDEX IF EXISTS idx_activity_sector_name;
            DROP TABLE IF EXISTS activity_sector;
```

Always put `public_id UUID NOT NULL UNIQUE` in the `CREATE TABLE`, as above.

And if your feature also needs a `workflow`/`process`/`step` row (a new demand type), heads up:
those tables want explicit ids and an explicit `public_id` in the raw seed SQL, unlike most other
seed rows. See the
[Enterprise Credit Workflow](enterprise-credit-workflow.md#the-workflowprocessstep-pipeline) doc
for why.

### 2. Entity: `datasource/<feature>/entity/`

`ActivitySectorEntity.java` (`datasource/sector/entity/`) is a plain JPA `@Entity`: private no-arg
constructor, getters/setters, `equals`/`hashCode` on id only. That's the standard JPA
entity-equality idiom, copy it verbatim. Don't reach for Lombok or records here: JPA entities have
to stay mutable and proxyable. If your table has a `public_id` column, generate it in a
`@PrePersist` hook (see `AuditLogEntity#generatePublicId` or `EarlyRepaymentEntity`). Never let the
client supply it.

### 3. Datasource: `datasource/<feature>/`

`ActivitySectorDatasource.java` is just a plain Spring Data JPA interface extending
`JpaRepository<Entity, Long>`. Add only the derived-query methods you actually need, 
`existsByNameIgnoreCase`, a custom `@Query`, whatever the feature calls for. No implementation to
write, Spring generates it for you.

### 4. Model: `model/<feature>/`

`ActivitySectorModel.java` is the domain type everything above the datasource layer actually works
with. For a simple feature, a record is enough (`ActivitySectorModel(Long id, UUID publicId, String
name, Instant createdAt)`). If the feature carries real business rules to protect, write a full
class with a validating `Builder` instead: see `model/bam/BamParametersModel` for that shape. This
is what `architecture.md` means by "rich domain model": any invariant your feature has ("rate must
be positive", "two dates must be ordered") gets enforced here, not in the service.

### 5. Entity Mapper: `datasource/<feature>/mapper/`

`ActivitySectorEntityMapper.java`: a `final` class, private constructor, two static methods
(`mapFromEntity(Entity) → Model` and `mapToNewEntity(...) → Entity`). It's the only place Entity and
Model types get imported together, which is exactly what keeps JPA annotations from ever leaking
into `model/`.

### 6. Repository interface + impl: `repository/<feature>/`

`IActivitySectorRepository.java`: the interface, using domain-level method names like
`create`/`findAll` rather than JPA vocabulary: plus `ActivitySectorRepository.java` (`@Repository`,
implements the interface, injects the `Datasource`, calls the `EntityMapper` going in and coming
out). This pair is the seam that hides JPA from `service/`. A service should never see
`JpaRepository`, `@Query`, or an `Entity` type.

### 7. Exception: `exception/`

One class per feature, for example `ActivitySectorException extends ApiException`, with a nested
`enum <Feature>ExceptionType` and a static `of(type)` factory (that's the Factory Method pattern,
see architecture.md). One enum value per distinct error case your service can throw.

### 8. i18n keys for the exception: `src/main/resources/i18n/exception/`

Four files: `<kebab-feature>.properties` / `_fr` / `_en` / `_ar` (root and `_fr` carry the same
French text, since French is the fallback locale). Keys are formatted
`<camelFeature>.<camelCaseReason>`, e.g. `activitySector.duplicateName`. There's no auto-scan for
this; like the DTO bundle two steps later, it needs a manual entry: add
`i18n/exception/<kebab-feature>` to the comma-separated list in
`src/main/resources/i18n/basenames.properties`. Skip that step and nothing errors, the message just silently falls back to the raw
`{...}` key, which is exactly why it's easy to miss. One more thing: if you ever touch response
encoding directly (raw `HttpServletResponse#getWriter()`), it needs an explicit UTF-8 charset or
accented characters (é, à, ...) come out mangled. Spring's own message resolution already handles
this correctly: it's only the custom low-level writes that bite you.

### 9. Service interface + impl: `service/<feature>/`

`IActivitySectorService.java` + `ActivitySectorService.java` (`@Service`) is where the business
logic actually lives: uniqueness/validation checks that need a repository lookup (they can't live
in the Model or the DTO validator), orchestrating the repository, and, if the action should be
audited, calling `IAuditService.log(actor, AuditAction.X, target, details)`: pass an `AuditTarget`
when the action is about a dossier, enterprise or user, and use `AuditChanges` for before → after
values. Add your action to the `AuditAction` enum first; if it touches money, credit decisions,
regulatory parameters, rights or bank details, also add it to the mandatory set there
(`AuditAction#isMandatory`). Write methods get `@Transactional`; read-only ones get
`@Transactional(readOnly = true)`.

A few rules every service follows:
- **Dates and times come from the injected `Clock`** (`clock.instant()`, `LocalDate.now(clock)`),
  never `Instant.now()`: business dates are Moroccan calendar days (`Africa/Casablanca`).
- **Notifications are sent after commit**: `afterCommit.send(() -> …)` (`AfterCommitNotifications`),
  wording through `NotificationTexts`.
- **No framework or library types** in a service (no `MultipartFile`, JavaMail, JJWT, Tika, Spring DAO
  exceptions): define a port interface in `service/`, implement it in `infrastructure/`. A unique-key
  race surfaces as `DuplicateEntryException` from the repository.

**Audit-timing gotcha, learned the hard way on this codebase**: if your service publishes a domain
event, or the audit call happens from something reacting `AFTER_COMMIT` to a
`@TransactionalEventListener`, the audit/notification write needs
`@Transactional(propagation = REQUIRES_NEW)`. Plain `REQUIRED` silently no-ops there, because it's
running inside a post-commit listener's stale transaction context. Simple in-line calls, like
`ActivitySectorService.createActivitySector` where the audit call sits in the same transaction as
the write, don't need any of this. Only reach for `REQUIRES_NEW` once you're inside an
`AFTER_COMMIT` listener.

### 10. Request/Response DTOs: `controller/dto/<feature>/{request,response}/`

**Always Java records.** That's the convention here as of Java 25 and it applies to every new or
edited DTO, no exceptions: don't write a class-based DTO even when it feels like it "just needs a
builder." Bean Validation annotations reference i18n keys
(`{validation.createActivitySector.name.notBlank}`), never hardcoded English strings. And add
`@Schema(description=..., example=...)` on every field; it's what feeds the Swagger UI other devs,
and the frontend team, will actually read.

### 11. i18n keys for DTO validation: `src/main/resources/i18n/dto/`

Same four-file pattern here: `create-<kebab-feature>-request(.properties|_fr|_en|_ar)`, keys
formatted `validation.<camelAction><Feature>.<field>.<rule>`. And just like the exception bundle in
the previous step, add `i18n/dto/create-<kebab-feature>-request` to the comma-separated list in
`src/main/resources/i18n/basenames.properties`: the "central basenames import trick."

### 12. Controller mapper: `controller/<feature>/mapper/`

`ActivitySectorControllerMapper.java` follows the same `final`-class/private-constructor/static-methods
shape as the entity mapper, just going `Model → ResponseDTO` this time. Controllers only ever
construct a `RequestDTO → primitives` call into the service, then map `Model → ResponseDTO` on the
way out. Don't pass an `Entity`, or a raw `RequestDTO` field-by-field, into a `Model` constructor
without going through a mapper.

### 13. Controller interface + impl: `controller/<feature>/`

`IActivitySectorController.java` is the Swagger-documented contract: `@Tag`, `@Operation`,
`@ApiResponses` per method, one entry per realistic HTTP status. `ActivitySectorController.java`
implements it: `@RestController`, `@RequestMapping("/api/v1/...")`, and one `@PreAuthorize` per
endpoint that isn't intentionally public (only a handful are: auth, the two simulations, invitations,
the activity-sector list, and the `dev`-only fake SMS gateway). Controller methods do **zero business logic**. Validate via
`@Valid`, call one service method, map the result, return `ResponseEntity`, done. If you catch
yourself writing an `if` that isn't about HTTP status or shape, that check belongs in the service
(step 9), not here.

## Quick reference: file checklist

Copy this straight into your PR description and check items off as you go.

- [ ] Liquibase changeset (`db.changelog-master.yaml`): table + rollback, `public_id UUID` column included
- [ ] `datasource/<feature>/entity/<Feature>Entity.java`
- [ ] `datasource/<feature>/<Feature>Datasource.java` (Spring Data JPA interface)
- [ ] `model/<feature>/<Feature>Model.java`
- [ ] `datasource/<feature>/mapper/<Feature>EntityMapper.java`
- [ ] `repository/<feature>/I<Feature>Repository.java` + `<Feature>Repository.java`
- [ ] `exception/<Feature>Exception.java`
- [ ] `i18n/exception/<kebab-feature>(.properties|_fr|_en|_ar)`
- [ ] `AuditAction` enum entry (if the action should be audited)
- [ ] `service/<feature>/I<Feature>Service.java` + `<Feature>Service.java`
- [ ] `controller/dto/<feature>/request/*RequestDTO.java` (records)
- [ ] `controller/dto/<feature>/response/*ResponseDTO.java` (records)
- [ ] `i18n/dto/<kebab-request-name>(.properties|_fr|_en|_ar)` **+ register in `basenames.properties`**
- [ ] `controller/<feature>/mapper/<Feature>ControllerMapper.java`
- [ ] `controller/<feature>/I<Feature>Controller.java` (Swagger contract) + `<Feature>Controller.java`
- [ ] Unit tests: repository, service, controller (mirror the existing `sector` package's test tree), with their values taken from `unittest/mock/data/`
- [ ] Karate `.feature` file if the endpoint needs live HTTP coverage (see [Testing](testing.md))

## Conventions that apply everywhere above

- **`I`-prefixed interfaces** for every repository/service/controller. Lets Spring inject the
  abstraction and keeps a consumer from depending on a concrete class it doesn't actually need.
- **Static mapper classes** (`final`, private constructor, static methods) at every DTO↔Model↔Entity
  boundary. Never a mapping library, never inline field-copying inside a controller or service.
- **`public_id` (UUID) is the only id ever exposed over the API.** The `BIGINT id` stays
  DB-internal, resolved server-side via `findIdByPublicId(UUID)`: don't let a `Long` id sneak back
  into a request/response DTO.
- **DTOs are always records.** No exceptions, new or edited.
- **No comments in the code.** Names carry the meaning; the reason behind a non-obvious choice goes in
  [Architecture: design notes](architecture.md#design-notes).
- **No literal business values in tests.** Usernames, names, amounts, rates, codes and dates come from the
  classes in `src/test/java/com/credit/bladi/unittest/mock/data/` ([Testing](testing.md#unit-tests)).
- **Dependency rule**: `model/` imports no framework; `service/` never imports `infrastructure/`,
  `datasource/` or `controller/`; controllers never touch repositories. See
  [Architecture → Layers](architecture.md#layers-and-dependency-rule).
- Follow the whole checklist even for a small feature. Each file is narrow (most are 10 to 50 lines); do not
  skip a layer, for example by calling the datasource from the service: `ArchitectureTest` fails the build.
